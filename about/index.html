Engineering at the failure boundary

My favorite engineering problems are rarely isolated algorithms. They are systems whose behavior changes under concurrency, partial failure, retries, uneven traffic or imperfect data. The useful question is not only “does it work?” but “what happens when one dependency is slow, an event is delivered twice, or a batch stops halfway through?”

That lens shapes how I design Java and Spring Boot services: make state transitions explicit, keep interfaces small, measure the critical path, and give operators enough context to understand a failure without reconstructing it from fragments.

Reliable software is software whose failure behavior was designed—not discovered in production.

How I make technical decisions

  • Start with invariants. Identify what must remain true through retries, duplicate messages and partial completion.
  • Prefer explicit boundaries. A small, observable contract is easier to operate than a clever abstraction spanning several services.
  • Measure before tuning. Latency percentiles, queue depth, database plans and consumer lag are more useful than intuition alone.
  • Design the recovery path. Dead-letter handling, idempotency and safe replay belong in the first design, not the incident follow-up.
  • Leave the system easier to understand. The best fix often becomes a reusable platform component, runbook or test.

Technology, chosen by constraint

My core stack is Java, Spring Boot, Kafka and PostgreSQL. Around it I work with Redis, Elasticsearch, MongoDB, RabbitMQ, SQS, Debezium, Kafka Connect, Docker and AWS services such as S3, Glue and Athena. I also use Python and Django when they fit the delivery problem better.

The tool is not the architecture. I choose technology around data ownership, delivery guarantees, failure isolation, operational cost and the skill set of the team that will support it.
