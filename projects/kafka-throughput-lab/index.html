Kafka Throughput Lab

A compact producer project for exploring JSON serialization, asynchronous delivery and the relationship between topic partitions and consumer parallelism.

Java 21Spring Boot 3.3.3Spring Kafka3 partitions

What the repository demonstrates

The project wires a Spring Boot HTTP API to a local Kafka broker. It creates a topic named softenggourav-demo with three partitions, serializes Customer objects as JSON, and publishes through Spring Kafka's KafkaTemplate.

The send API returns a CompletableFuture<SendResult>. A completion callback records the assigned offset or the delivery error, keeping the request thread out of the broker round trip.

Producer and topic configuration

The configuration uses StringSerializer for keys and Spring Kafka's JsonSerializer for values. The bootstrap server is local, and the topic is declared as a Spring bean:

@Bean
public NewTopic createTopic() {
    return new NewTopic("softenggourav-demo", 3, (short) 1);
}

@Bean
public KafkaTemplate<String, Object> kafkaTemplate() {
    return new KafkaTemplate<>(producerFactory());
}

Three partitions create room for three active consumers in one group. That does not automatically produce three-way balance: the record key and partitioner decide where records land, and a null key typically spreads events according to producer behavior rather than a business ordering rule.

A lab, not a published benchmark

The repository describes a one-million-record experiment, but the current checkout is best understood as the producer foundation for that experiment—not a reproducible benchmark report. It does not yet publish hardware details, broker settings, consumer code, latency percentiles or result files.

A throughput number without workload shape, durability settings and measurement boundaries is not portable evidence.

That distinction matters. Kafka throughput changes dramatically with record size, compression, batching, acknowledgements, replication, storage, network latency and consumer work. A credible lab should make all of those variables visible.

How I would run the million-record experiment

  1. Define the payload. Fix the serialized byte size and key distribution so runs are comparable.
  2. Warm the system. Run a short warm-up before collecting JVM and broker metrics.
  3. Bound the producer. Generate a known record count while recording accepted, acknowledged and failed sends separately.
  4. Capture percentiles. Report p50, p95 and p99 end-to-end latency alongside records and bytes per second.
  5. Vary one parameter at a time. Compare batch.size, linger.ms, compression, acks and in-flight requests without mixing changes.
  6. Observe the consumers. Record lag, rebalance duration, processing time and partition assignment for one, two, three and four consumers.

Explore the source

The repository is intentionally approachable: view it on GitHub, run Kafka locally on port 9092, then start the Spring Boot service on port 9191. The best next contribution is a repeatable benchmark harness with consumer implementations and machine-readable result output.
