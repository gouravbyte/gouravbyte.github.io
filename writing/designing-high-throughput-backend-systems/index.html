Designing high-throughput backend systems

The fastest path is rarely “add threads.” Start with a work budget, find the constrained stage, and make overload behavior part of the design.

By Gourav BarnwalPublished Sep 9, 2026Intermediate

Turn the goal into a budget

“Process 60,000 records in five minutes” is a useful start because it implies an average completion rate of 200 records per second. It is not yet a design. We still need record size, work per record, acceptable failure rate, ordering constraints, burst shape and durability requirements.

Write the target as a budget:

  • 60,000 input records must reach a terminal state within 300 seconds.
  • At least 99.9% should complete automatically; failures must remain replayable.
  • No entity may receive the same non-idempotent side effect twice.
  • The database must stay within agreed CPU, I/O and connection limits.
  • Progress and failure causes must be visible while the batch is running.

The average rate is the floor. Capacity must include startup, skew, retries and the slowest realistic dependency period.

Model the work as stages

Measure stages separately. If reading 60,000 rows takes 12 seconds, transformation 30 seconds and downstream writes 420 seconds, tuning the reader cannot meet the five-minute target. The write stage controls the system.

Queues between stages absorb short variance but also hide saturation. Bound every queue and record its age. An unbounded executor is not capacity; it is deferred failure plus memory pressure.

Batch where fixed cost dominates

Batching amortizes network round trips, transaction setup, serialization framing and protocol overhead. It helps when the fixed cost per request is meaningful compared with the work per item.

Large batches are not always better. They consume memory, hold locks longer, increase retry scope and produce uneven latency. Find the knee of the curve by testing several sizes against throughput and p99 completion time.

Batch invariant

A failed batch must have a defined retry unit. If the whole batch repeats, every per-record effect must be idempotent.

Add bounded concurrency

Concurrency overlaps waiting. It improves throughput when workers spend time on I/O and dependencies have unused capacity. It makes performance worse when workers compete for the same saturated connection pool, lock or CPU.

A practical worker count starts from measured service time and target rate, then is capped by downstream limits. If each remote call averages 100 ms and the target is 200 calls per second, roughly 20 calls must be in flight before overhead and headroom. If the downstream permits only 12 concurrent requests, the target is impossible without batching, a faster endpoint or changed requirements.

Use separate bounded executors for workloads with different behavior. A slow report export should not occupy the same pool that serves short interactive requests.

Backpressure protects useful work

When input exceeds sustainable completion, the system must slow admission, buffer within a known limit or reject work clearly. Continuing to accept everything turns a temporary spike into rising latency, timeouts, retries and a wider failure.

  • Pause or slow queue consumers when database saturation crosses a threshold.
  • Use broker lag as a buffer only when retention and recovery time are acceptable.
  • Return a clear overload response before every thread and connection is exhausted.
  • Add jitter to retries so recovering dependencies do not receive synchronized bursts.
  • Prioritize interactive or deadline-bound work over best-effort bulk work.

Make retries a normal path

Distributed work can fail after the effect succeeds but before the caller receives confirmation. Retrying is necessary; duplication is therefore a design case, not an anomaly.

Assign each logical command an idempotency key. Store the key and result with the business transaction, protect it with a uniqueness constraint, and return the existing outcome on replay. For event consumers, the event ID and handler name can form the deduplication key.

A retry policy should classify errors. Validation failures and violated business rules will not improve with time. Timeouts, temporary unavailability and selected conflicts may. Bound attempts, use exponential delay with jitter and route exhaustion to a visible recovery queue.

Protect the database

The database is frequently the shared constraint. Performance work should include query plans, index selectivity, lock duration, connection usage, WAL volume and storage latency.

TechniqueBenefitFailure mode to watch
Bulk insert/updateFewer round tripsLarge transactions and lock duration
Keyset paginationStable work chunksIncorrect ordering or missing tie-breaker
Covering indexLess heap accessWrite amplification and storage growth
More connectionsMore concurrent I/O to a pointContention, context switching and overload
Read replicaSeparates eligible readsReplication lag and stale decisions

Use an explicit claim pattern when several workers pull rows from one table. The claim must prevent two workers from owning the same row while allowing abandoned work to become eligible again after a lease or state transition.

Measure end-to-end completion

Track accepted, started, completed, retried and failed records. Measure queue age and end-to-end completion latency, not only the duration of one method. Separate percentiles by outcome and dependency.

At minimum, graph:

  • records and bytes completed per second;
  • p50, p95 and p99 completion latency;
  • active workers, queue size and oldest-item age;
  • database pool use, query latency and lock waits;
  • downstream rate-limit responses, timeouts and retry attempts;
  • permanent failure count and replay age.

Prove the design under realistic load

  1. Generate representative record sizes and key distributions.
  2. Warm the runtime and dependency caches before measurement.
  3. Increase rate gradually to find the first saturation signal.
  4. Hold the target long enough to expose leaks, queue growth and compaction effects.
  5. Inject dependency latency, process restarts and partial failure.
  6. Replay failed work and prove the final business counts reconcile.

Report configuration and environment with every result. Throughput without CPU, memory, storage, payload, durability and dependency settings is a number that cannot guide another design.

A reliable optimization sequence

Define the target, instrument the current path, identify the constrained stage, reduce unnecessary work, batch fixed costs, add bounded concurrency, introduce backpressure, make retries safe, and test failure. Repeat from measurements.

High throughput is sustained completed work—not accepted requests, queued futures or optimistic log lines.
