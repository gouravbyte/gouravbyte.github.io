Kafka consumer groups explained with a real partition model

The useful mental model is not “Kafka distributes messages.” It is “a group temporarily owns partitions, and ownership controls ordering, parallelism and recovery.”

By Gourav BarnwalPublished Sep 9, 2026Intermediate

Start with ownership, not consumers

A Kafka topic is split into partitions. Within one consumer group, each partition is assigned to at most one active consumer at a time. That rule creates the central trade-off: partitions preserve order, while partition count places an upper bound on useful parallelism for that group.

Imagine an orders topic with six partitions and a group called risk-evaluator containing three consumers:

ConsumerAssigned partitionsRecords it can process
C1P0, P1All records currently in P0 and P1
C2P2, P3All records currently in P2 and P3
C3P4, P5All records currently in P4 and P5

Each partition remains ordered, but the topic as a whole does not have a global order. If all events for one order must stay ordered, use the order ID as the record key so the producer consistently selects the same partition.

What happens when consumers scale

Add C4 and the group coordinator redistributes six partitions across four consumers. Some consumers receive two partitions and some one. Add C7 and one consumer must remain idle because only six partitions exist.

Consumer count can use available partition parallelism; it cannot create more of it.

More partitions are not free. They increase broker metadata, open files, leader-election work and the number of units moved during assignment. Pick a count that accounts for expected throughput and future consumer concurrency, then validate it with the actual workload.

A rebalance is a temporary ownership change

A group may rebalance when a consumer joins, leaves, exceeds its poll interval, changes subscription or when topic partitions change. During an eager rebalance, consumers revoke current assignments before new work proceeds. Cooperative assignment can reduce movement by transferring only the partitions that need a new owner.

For our six-partition example, suppose C2 stops sending heartbeats. After the session timeout, its P2 and P3 assignments become eligible for reassignment. The surviving consumers do not safely continue those partitions from memory; they resume from committed offsets.

Operational consequence

Frequent rebalances are not background noise. They reduce useful processing time and can amplify duplicate work around the handoff boundary.

Common causes include slow record processing, long stop-the-world pauses, network interruption, rolling deployments and a max.poll.interval.ms that is too small for the largest processing batch.

Offsets separate progress from processing

An offset identifies a record's position within one partition. A consumer reads at a current position; the group stores a committed position used for recovery. Those are related but not identical.

  • Commit before the side effect: a crash can lose work because recovery starts after a record whose effect never completed.
  • Commit after the side effect: a crash between the effect and commit can replay the record.
  • Commit a batch: fewer commits improve throughput, but a failure can replay more records.

For most business processing, at-least-once delivery plus an idempotent handler is a robust default. The consumer records the business result and a deduplication marker in one database transaction, then commits Kafka progress after that transaction succeeds.

Make replay safe

A handler is idempotent when applying the same logical event again does not create an extra business effect. A practical pattern uses a stable event ID and a uniqueness constraint:

begin;

insert into processed_event(event_id)
values (:event_id)
on conflict do nothing;

-- Apply the business change only when the insert succeeded.

commit;

The uniqueness constraint turns concurrent or repeated delivery into a database decision rather than a race in application memory. For external side effects such as payments or email, pass an idempotency key to the downstream system or separate intent recording from dispatch with an outbox.

Lag is useful, but incomplete

Consumer lag is the distance between the latest partition offset and the group's committed offset. Rising lag tells you that arrival currently exceeds acknowledged processing. It does not explain why.

Monitor lag beside processing latency, poll duration, error rate, retry volume, rebalance count, assigned partition count and dependency latency. A group with low lag but frequent errors may be skipping work; a group with controlled lag may be absorbing a known traffic burst exactly as designed.

A production checklist

  1. Choose record keys from ordering requirements, not convenience.
  2. Size partitions from measured throughput and expected group concurrency.
  3. Keep polling responsive; move slow work to bounded workers when appropriate.
  4. Disable automatic commits when the business completion boundary must be explicit.
  5. Make handlers idempotent before relying on retries.
  6. Bound retries and route exhausted records with enough context for safe replay.
  7. Alert on sustained lag and rebalance churn, not a single noisy sample.
