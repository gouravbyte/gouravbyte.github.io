A scalable Spring Boot architecture

Scale starts with explicit boundaries and measurable work. A service split is a deployment decision that should come later, when the evidence can pay for its coordination cost.

By Gourav BarnwalPublished Sep 9, 2026Intermediate

Start with a modular application

For a new business system, a well-structured Spring Boot application is often the best starting point. It keeps one deployment and one debugging surface while allowing the code to express real domain boundaries.

Organize by capability rather than framework layer. A package such as loan.application should expose use cases, contain domain rules and depend on interfaces for persistence or messaging. It should not reach into another capability's repository because both happen to run in one JVM.

com.example.platform
├── loan
│   ├── api
│   ├── application
│   ├── domain
│   └── infrastructure
├── customer
├── payment
└── shared

Keep shared small. A global utility package easily becomes a hidden coupling layer where domain concepts lose ownership.

Make the request path boring

A synchronous request should validate input, authenticate the caller, execute one bounded use case, commit one clear transaction and return. Expensive fan-out, report generation and bulk I/O should not quietly occupy request threads.

Set timeouts at every remote boundary and make the overall request budget smaller than the caller's timeout. A connection pool, HTTP client and executor are finite queues; exposing their saturation is part of the API's correctness.

Keep transaction boundaries visible

Place transactions around application use cases, not every repository method. That makes the business atomicity boundary visible and avoids accidental partial updates.

Do not hold a database transaction open while calling an unpredictable remote service. Prefer a state transition such as PENDING, commit it, perform remote work with an idempotency key, and complete the transition in another bounded operation.

Useful question

If the process stops after this database commit but before the next line, what durable state tells recovery what to do?

Move the right work asynchronously

Asynchronous processing is useful when the caller does not need the final result immediately, work can be retried, bursts should be buffered or several independent consumers need the same event. It is not a way to make failure disappear.

When a database change and an event must agree, write an outbox row in the same transaction as the domain state. A publisher then forwards the outbox record to Kafka or another broker. Consumers must still be idempotent because delivery can repeat.

  • Give events stable IDs and versioned schemas.
  • Key events by the entity whose order matters.
  • Bound retries and separate transient from permanent failures.
  • Expose queue age and consumer lag, not only queue length.

Treat the database as a system, not an annotation

JPA makes common persistence convenient, but the database still executes queries, acquires locks and maintains indexes. Review generated SQL for critical paths. Use pagination that remains stable, select only required columns for high-volume reads, batch writes deliberately and inspect query plans with production-like distributions.

Connection pools should be sized from database capacity and request behavior, not CPU count alone. A very large pool can increase contention and make overload slower rather than faster.

Instrument the business path

Technical metrics answer “is the service healthy?” Business-flow metrics answer “is the platform completing work?” Both are required.

SignalExamplesQuestion answered
Trafficrequest rate, event arrival rateHow much work is arriving?
Latencyp50, p95, p99 by operationWho is waiting, and how long?
Saturationpool usage, queue depth, lagWhich finite resource is full?
Correctnessrejected transitions, duplicate eventsIs work producing valid outcomes?
Completionloans processed, exports finishedIs the business flow progressing?

Use correlation IDs across logs, traces and messages, but never place secrets or unnecessary personal data in observability fields.

Test boundaries, not implementation trivia

  • Unit tests: domain rules and state transitions without Spring.
  • Slice tests: controller contracts, serialization and repository queries.
  • Integration tests: real PostgreSQL or Kafka behavior through containers.
  • Contract tests: compatibility at external HTTP and event boundaries.
  • Load tests: the complete critical path with realistic payloads and dependency limits.

Failure tests are especially valuable: duplicate an event, delay a dependency, exhaust the connection pool, restart a consumer mid-batch and verify that recovery preserves the invariant.

When to extract a service

Extract a module when it needs independent scaling, release cadence, security isolation, technology constraints or ownership—and when the team can operate the new network boundary. Avoid extraction merely because a package has grown large.

A strong module makes a strong service candidate because its data ownership, interface and tests already exist. A weak module moved over HTTP becomes a distributed weak boundary.

For the performance side of this architecture, continue with designing high-throughput backend systems.
