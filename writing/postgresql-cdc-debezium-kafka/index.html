PostgreSQL CDC using Debezium and Kafka

Change data capture is not “poll the table faster.” It is a durable progress pipeline from the database write-ahead log to consumers that must tolerate replay.

By Gourav BarnwalPublished Sep 9, 2026Intermediate

The data path

PostgreSQL records durable database changes in its write-ahead log, or WAL. Logical decoding turns that log into a stream of row-level changes. A Debezium PostgreSQL connector reads the logical replication stream, converts changes into structured records and writes them to Kafka topics.

The connector also stores progress. PostgreSQL tracks a replication slot so WAL needed by the connector is retained, while Kafka Connect stores connector offsets so a restarted task can resume from a known log position.

What a change event represents

A Debezium envelope normally includes the row state before and after a change, an operation code, source metadata and a timestamp. Inserts, updates and deletes remain distinguishable; a tombstone may follow a delete depending on configuration and compaction behavior.

That envelope is infrastructure truth, not automatically a stable business contract. A database column rename, internal status code or table split can leak implementation changes to every downstream consumer.

Contract decision

Use raw CDC when consumers intentionally mirror database state. Use a transformation or transactional outbox when consumers need a durable business event such as LoanApproved.

The initial snapshot boundary

Before streaming ongoing changes, a new connector may snapshot existing rows. The difficult part is not reading rows; it is establishing a consistent boundary so no change is lost between the snapshot and the log stream.

Plan the snapshot as an operational event:

  • Estimate table scan time and load on the primary database.
  • Decide whether consumers can distinguish snapshot rows from live changes.
  • Verify that the replication slot and WAL retention can survive the snapshot duration.
  • Record row counts and source positions so completeness can be reconciled.
  • Test restart behavior during the snapshot, not only after it.

Ordering and transactions

PostgreSQL commits a transaction atomically, but Kafka consumers often observe table topics independently. Ordering is preserved only within a Kafka partition, and the record key determines partition placement.

For one table keyed by entity ID, changes to the same entity can remain ordered in one partition. Cross-table business invariants are harder. If a transaction updates an application row and an audit row, two topic consumers must not assume globally synchronized arrival.

When a business event must describe the transaction as one intentional unit, an outbox row written in the same database transaction gives Debezium one well-defined record to publish.

Schema evolution without surprise

CDC makes database schema a distributed dependency. Before a migration, identify which fields downstream systems actually consume and how the serialization layer represents defaults, nullability and type changes.

Add nullable columnOlder consumers may ignore it safelyAdd, deploy tolerant readers, then start using it
Rename columnAppears as remove plus addDual-publish or transform during a compatibility window

Recovery and replay

Debezium and Kafka are designed around resumable progress, which means duplicates must be expected around failures. A connector can publish a record and fail before its offset is durably acknowledged. A consumer can commit a business transaction and fail before committing its Kafka offset.

Consumers should therefore use stable source identifiers—such as topic, partition and offset or a business event ID—to make effects idempotent. Rebuild workflows should define where replay starts, which sinks must be cleared or versioned, and how completion is reconciled.

What to monitor

  • Replication slot lag and retained WAL bytes: a stalled connector can exhaust database storage.
  • Connector/task state: failed and paused tasks require different responses.
  • Source-to-Kafka delay: distinguish database inactivity from capture latency.
  • Kafka producer errors and topic growth: the connector is also a Kafka producer.
  • Consumer lag and dead-letter volume: publication is not end-to-end completion.
  • Schema history health: recovery depends on reconstructing the schema at each log position.

Give the connector a database role with only the required replication and table privileges, protect Kafka credentials, encrypt network paths and treat change events as production data. CDC often contains every sensitive field in the captured table.

When CDC is the right tool

Use CDC when several systems need timely database changes, a search or analytics projection must stay synchronized, or adding application-level publishing to every write path is impractical. Avoid it when a small scheduled export is sufficient, when row-level data must not leave the database, or when the only valid contract is a carefully curated domain event.

The reliable design is less about installing a connector and more about owning progress, compatibility and replay across the whole path. For the consumer side of that path, continue with Kafka consumer groups and idempotent processing.
